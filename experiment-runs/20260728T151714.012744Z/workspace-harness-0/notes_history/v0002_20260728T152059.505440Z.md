# Working notes

## Objects
- 64x64 scene with a 5x5 moving token. Its normal sprite is color 12 on its top two rows and color 9 on its bottom three rows.
- Static terrain uses colors 3/4/5. The token currently occupies x=34..38, y=20..24.
- Rows 61..62 contain a progress meter: each effective control input changes the leftmost color-11 column to color 3.
- A patterned target/terminal occupies the token lane around y=15..19.
- A horizontal color-3 corridor crosses the vertical lane at y=25..29.

## Mechanism hypotheses
- ACTION1 moves the token upward by exactly 5 pixels; ACTION2 moves it downward by exactly 5 pixels.
- Successful vertical movement advances the bottom meter by one column. A blocked ACTION1 at the upper endpoint changes neither token nor meter.
- ACTION3 at y=20 left the token fixed but advanced the meter. H1: it is a horizontal move blocked because the token is not aligned with the y=25 corridor. H2: it is a rotate/interact command whose only visible effect here is meter consumption.
- ACTION4 is wholly untested and may be the opposite horizontal direction or another rotate/interact control.
- Goal likely requires navigating the corridor network to a patterned endpoint; merely reaching the upper terminal did not complete the level.

## Experiments and evidence
- Repeated ACTION1 moved the token upward in 5-pixel increments to y=15; another ACTION1 there was a complete no-op.
- ACTION2 moved it downward in 5-pixel increments and advanced the meter.
- ACTION3 at x=34,y=20 advanced the meter by one column without moving or changing the sprite, ruling out an unrestricted horizontal translation there.
- Full backtest passes 15 transitions with ACTION3 modeled as stationary meter advancement in the observed context.
